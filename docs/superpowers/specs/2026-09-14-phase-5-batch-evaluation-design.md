# Phase 5前半：複数経路の一括評価とプレゼンテーションUI設計

## 目的

Phase 4で実装した5種類の経路選定モデルを、単一の出発地・目的地だけでなく、複数のODペアで再現可能に評価する。あわせて、安全性要素とOSM属性欠損要素の重みを変化させ、経路と指標がどの程度変わるかを定量化する。

本工程では評価基盤を先に整え、地図上の注意地点表示やルート選定理由の説明機能は後続工程とする。Web画面は途中発表で結果を読み取りやすい構成へ整理するが、新しい研究指標の画面表示は追加しない。

## 成果物

### 入力

- `data/input/od_pairs.csv`
  - 東京駅周辺3 kmの道路グラフを対象とする20組のODペア
  - Git管理対象とし、同じ入力で再評価できるようにする
- `data/raw/sample_bike.graphml`
  - OSMnxで取得した道路グラフ
  - 既存方針どおりGit管理外とする

  - 20組×5プロファイルの通常評価を実行する

生成結果は既存方針どおりGit管理外とし、コマンドから再生成できるようにする。

### 簡易起動

## ODペアの設計

対象地域は東京駅を中心とする半径3,000 mとする。Phase 4で使用した地域と一致させ、既存結果との比較を可能にする。

20組は道路グラフ上のノード座標から選び、特定方向や距離へ偏らないようにする。ODペアCSVは次の列を持つ。

| 列 | 内容 |
|---|---|
| `od_id` | `OD-01`から`OD-20`までの一意な識別子 |
| `origin_label` | 出発地点の表示名 |
| `origin_lat` | 出発地点緯度 |
| `origin_lon` | 出発地点経度 |
| `destination_label` | 目的地点の表示名 |
| `destination_lat` | 目的地点緯度 |
| `destination_lon` | 目的地点経度 |
| `distance_band` | `short`、`medium`、`long`の選定区分 |

距離帯は直線距離を選定基準とし、短距離5組、中距離10組、長距離5組を基本配分とする。各座標は実行時に最寄りノードへスナップする。次の条件を満たさない候補は入力へ採用しない。

- 出発ノードと目的ノードが異なる
- 距離最短プロファイルで到達可能
- 同じスナップ後ノード対が重複しない
- 地域の一方向だけへ集中しない

地点名は実験用であることが分かる簡潔なラベルとし、実在施設名の正確性に依存させない。

## 評価モデルの拡張

既存の`ROUTE_PROFILES`は標準設定として維持する。評価関数へプロファイル設定を明示的に渡せるようにし、感度分析時にグローバル変数を書き換えない。

既存APIとの互換性を保つため、設定が省略された場合は現在の標準設定を使う。Web APIの入出力形式と5プロファイルのIDは変更しない。

`information`プロファイルの表示名だけを「情報信頼性優先」から「OSMデータ充足度優先」へ変更する。IDはCSV、API、JavaScriptとの互換性を保つため`information`のままとする。

経路同一性は、選択された有向エッジの`(u, v, key)`を順番どおりに並べた値から安定したシグネチャを作って判定する。ノード列だけでは、並行エッジが異なる経路を誤って同一と判断する可能性があるため使用しない。

## 通常評価

各ODペアに対して5プロファイルを計算し、利用可能な経路ごとに次の列を出力する。

- OD情報と入力座標
- スナップ後の出発・目的ノード
- プロファイルIDと表示名
- 経路利用可否とエラー内容
- 距離
- 距離最短経路からの距離増加率
- 幹線道路率
- 自転車レーン率
- 信号数
- OSM属性不明率
- プロファイル仮コスト
- 経路シグネチャ
- 距離最短経路と同一か
- 同じ経路を選んだプロファイル数と割合
- OD内のユニーク経路数

距離増加率は次式で計算する。

```text
(対象プロファイル距離 - 距離最短経路距離) / 距離最短経路距離 × 100
```

利用不能なプロファイルについても1行を残し、`available=false`とエラー内容を記録する。距離最短経路自体が存在しないODは、そのODの5行すべてを利用不能として記録し、他のOD評価は継続する。

## 感度分析

安全性要素と属性欠損要素を独立に変化させる。倍率は次の3段階とする。

| 水準 | 倍率 |
|---|---:|
| `weak` | 0.5 |
| `medium` | 1.0 |
| `strong` | 2.0 |

安全性倍率は`road_type`と`cycleway`へ、属性欠損倍率は`unknown`へ適用する。各プロファイルが持つ標準重みの比率は維持する。距離最短プロファイルはすべての追加重みが0のため、どの感度設定でも変化しない。

全9組合せを各OD・各プロファイルへ適用する。`sensitivity_analysis.csv`は通常評価と同じ主要指標に加え、次の列を持つ。

`medium`×`medium`を標準設定として扱い、既存の`ROUTE_PROFILES`と同じ重みになるようにする。

- `safety_level`、`safety_multiplier`
- `unknown_level`、`unknown_multiplier`
- 標準設定で選ばれた経路と同一か
- 標準設定からの距離変化率

`sensitivity_summary.csv`は感度設定×プロファイル単位で次を集計する。

- 評価OD数と利用可能OD数
- 平均距離増加率
- 平均幹線道路率
- 平均自転車レーン率
- 平均信号数
- 平均OSM属性不明率
- 標準設定から経路が変わったODの割合

## CLIとエラー処理

評価スクリプトはプロジェクト直下からモジュールとして実行する。

```powershell
.\.venv\Scripts\python.exe -m backend.scripts.evaluate_profiles
```

既定パスを用意し、通常利用では引数を不要にする。必要に応じてGraphML、OD CSV、各出力先をコマンドライン引数で差し替えられるようにする。

次の入力不備は、処理開始前に明確な日本語エラーとして終了する。

- GraphMLまたはODペアCSVが存在しない
- 必須列が不足している
- OD IDが重複している
- 座標が数値でない、または緯度・経度の範囲外
- ODペアが0件

個別ODの到達不能は全体エラーにせず、出力行へ記録する。出力先ディレクトリは存在しなければ作成する。

## プレゼンテーションUI

画面を研究ダッシュボードとして再構成する。

- ヘッダーから「テストページ」を削除する
- タイトルを「自転車経路比較」に変更する
- サブタイトルは「距離・ルール・安全性・OSMデータ充足度」の1行に限定する
- APIと道路データの状態を小さなステータス表示にする
- デスクトップでは地図を左、地点選択と主要指標を右に配置する
- 比較表は地図の下で画面幅を使って表示する
- 比較表に信号数を追加する
- 選択中の経路を色と行の強調で一致させる
- 長い研究説明文を削除し、フッターへ「研究用・暫定評価」とだけ表示する
- 画面幅が狭い場合は地図、操作、比較表の縦並びへ切り替える

地図操作、既存DOM ID、キーボード操作、Leafletの経路選択動作は維持する。

## 簡易起動

`start_app.cmd`はプロジェクト直下へ移動し、`.venv\Scripts\python.exe`とGraphMLの存在を確認してからWebアプリを起動する。不足時は日本語の短い対処方法を表示して終了する。

`run_evaluation.cmd`も同様に仮想環境、GraphML、ODペアCSVを確認し、一括評価スクリプトを実行する。終了後は生成ファイルの場所を表示する。

どちらも絶対パスや仮想環境の有効化を必要とせず、リポジトリを移動しても使用できる相対パス構成とする。

## テスト方針

Pythonの動作変更はテスト駆動で実装する。

- ODペアCSVの正常読込と各入力エラー
- 標準プロファイル設定を渡したときの既存結果との一致
- カスタム重みがグローバル標準設定を変更しないこと
- 距離増加率の計算
- 並行エッジを含む経路シグネチャと同一経路判定
- 到達不能なODでも残りの評価が継続すること
- 通常評価の行数と必須列
- 感度分析9組合せの行数と水準
- 感度集計の平均値と経路変更率
- 「OSMデータ充足度優先」への表示名変更
- プレゼンテーションUIの必須要素と削除対象文言

実装後は次を統合確認する。

1. 全バックエンドテスト
2. 東京駅周辺3 kmのOSM取得
3. ODペア20組の距離最短経路到達性
4. 通常評価100行の生成
5. 感度分析900行と感度集計45行の生成
6. 各CSVの必須列・欠損・数値範囲
7. FastAPIの起動、地図、5経路、比較表のブラウザ確認
8. 簡易起動ファイルの前提条件チェック

## 非対象

- 重みの妥当性確定
- 法的な違反判定
- 地図上の注意地点表示
- ルート選定理由の自然言語説明
- データベース導入
- React等へのフロントエンド移行
- 評価結果をWeb画面から実行・閲覧する機能

これらは一括評価と感度分析の結果を確認した後の工程とする。
